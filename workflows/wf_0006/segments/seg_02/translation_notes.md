# wf_0006 / seg_02 — translation notes

One assumption per line. Nothing below has been checked against a real Alteryx engine or a real
Snowflake account; every claim is against `docs/reference/simulator-semantics.md` (the parity
oracle) and program spec §8.

- This segment's output target is `snowpark`, so its source of truth is `proc.py` and `proc.sql` is only the `LANGUAGE PYTHON` wrapper `scripts/render_snowpark.py` produces from it. Editing `proc.sql` by hand edits nothing that runs; edit `proc.py` and re-render.
- **Which tool needed pandas, and why.** Tool 3 is the Python tool, and its script keeps a deferred balance that carries from one period to the next inside a customer and resets when a period is cancelled. That is a sequential recurrence over an ordered group, not a set expression: each row's cap check reads the balance the row before it left behind. It is expressible as a window only by first expressing the recurrence, and `min(carried + billed, cap)` does not distribute over a running sum, so there is no `SUM(...) OVER (...)` that produces it. The tool is therefore translated as itself — the same pandas loop — rather than rewritten, which is exactly the case the `snowpark` output target exists for.
- `scripts/target_check.py` reaches the same conclusion mechanically: `plugin_map.TARGET_CLASS` classifies a `python` node as `snowpark`, and a segment holding one is `snowpark`. Nothing here overrode it; the analyzer may only lower a proposed target, never raise it.
- **`to_pandas()` is bounded by the segment's own row count.** The handler reads `MIG_WORK.WF0006_SEG_01_OUT` — one row per billed customer-period, which `contract.inputs[0].expected_rows` bounds at 5,000,000 and `large` records as `false` — and materialises it in the procedure's memory. This is safe *because* of that bound, not in general: the same code against an unbounded stream would be a defect, and a segment whose input is `large` must not be translated this way.
- The script sorts by `["CUSTOMER", "PERIOD"]` itself before grouping, so the result does not depend on the order Snowflake returns rows in — which is unordered, and need not match the order the Alteryx engine read the yxdb in. `(CUSTOMER, PERIOD)` is unique on the incoming stream in every golden set (`contract.inputs[0].keys`), so that sort is total and the recurrence is reproducible. `contract.ordering` records the same pair and names `RECOGNIZED` and `DEFERRED` as the order-dependent columns.
- `groupby("CUSTOMER", sort=False)` keeps the groups in first-appearance order of the already-sorted frame, which is ascending `CUSTOMER`. `sort=False` is therefore not a divergence from Alteryx; it only avoids sorting a frame that is already sorted.
- A cancelled period zeroes the carried balance **before** that period's own cap is applied, so a cancellation changes `RECOGNIZED` as well as `DEFERRED`. `broken_sql/seg_02/01_cancellation_reset_ignored.py` is this rule deleted, and `broken.json` records what the validator says about it.
- pandas `groupby` drops rows whose key is NULL, so a NULL `CUSTOMER` would vanish silently rather than form a schedule of its own. That is why `CUSTOMER` is declared `NOT NULL` on the outbound stream. Nothing upstream guarantees it: the Filter in `seg_01` guarantees `BILLED` only. A NULL `CUSTOMER` would be a silent row loss in Alteryx too — this is a faithful translation of that behaviour, not an improvement on it.
- A NULL `CAP` that survived the Filter is silently **not** a cap, identically on both engines: `float(NULL)` is `nan` (the column comes back `float64` with `NaN` on both sides), and `min(x, nan)` returns `x`, so the row recognizes everything billed and carries nothing forward. Nothing raises and nothing diverges, so a parity run could never surface it — it is a data-quality risk in the source, named here rather than guarded against. (Measured, not assumed: `min(120.0, float("nan"))` is `120.0`.)
- A NULL `CANCELLED` is the one place the two engines disagree by default, and the procedure is written to remove the disagreement. The simulator types a `Bool` column as pandas' nullable `boolean`, where `bool(pd.NA)` raises `TypeError: boolean value of NA is ambiguous` — the Alteryx script fails on that row. The Local Testing Framework's `to_pandas()` hands back an `object` column holding `None`, where `bool(None)` is quietly `False` — the procedure would treat the row as not cancelled and write a number nobody asked for. A migration must not turn a loud failure into silent output, so `proc.py` tests `pd.isna(row["CANCELLED"])` first and raises; `validate_snowpark.py` reports that as a FAIL for the golden set that carries such a row.
- No golden set carries a NULL `CANCELLED`, and none can: the simulator would raise inside the Python tool before it could write the stream, so there is no expected output to compare against. The guard is therefore reasoned, not exercised.
- **Unverified:** how *real* Alteryx types a NULL `Bool` field inside the Python tool. The nullable `boolean` dtype above is `scripts/dev/alteryx_sim.py`'s choice and this project's assumption — the same register as every other simulator-semantics assumption (spec §9), to be checked against an engine when one is available.
- A narrower asymmetry, observed while checking the above and recorded for completeness: if a `Double` column were NULL in **every** row, the framework's `to_pandas()` gives an `object` column of `None` rather than `float64`/`NaN`, and `float(None)` raises. It cannot arise here — that would need a golden set in which no surviving row has a `CAP` at all — but it is why the `CAP` claim above is stated for the mixed column this workflow actually has.
- The source this was translated from is tool 3's `<Script>`, which is `tests/test_alteryx_sim_python.py::SCRIPT` with its **last three lines changed** — an explicit output column list plus `float64` casts, so the `empty` golden set keeps a schema instead of producing a column-less frame (`samples/wf_0006/README.md` gives the before and after). Task 1's test constant was deliberately left unchanged. Nothing above those three lines differs, and this module mirrors the script's loop exactly.
- `pd.isna(row["BILLED"])` is carried over from the Alteryx script unchanged, and on this workflow it can never be true: `seg_01`'s Filter has already removed every NULL `BILLED`. It is kept rather than simplified away so that `proc.py` reads as the same program the Python tool runs — a reader comparing the two should find no differences to explain.
- The output schema is declared explicitly as a `StructType` rather than inferred, for two reasons. The empty golden set produces no rows at all, and an inferred schema over no rows has no columns — the comparison would then fail on a schema difference that says nothing about the translation. And an inferred schema would give `RECOGNIZED`/`DEFERRED` whatever type the first row implies, where the contract requires `FLOAT`.
- `StringType(254)` and `DoubleType()` are what `lib/types_map.py` maps `VARCHAR(254)` and `FLOAT` to, and `snowpark_to_alteryx` maps them straight back, which is what lets `scripts/validate_snowpark.py` read the real table's schema off Snowpark and compare it with the golden file's. The columns are written in the contract's own order — the `StructType` must list the columns in the contract's declared `outputs[].columns` order: a different order is a schema FAIL, reported as a `TYPE` difference rather than as an ordering one.
- `mode("overwrite")` is what makes the segment idempotent: the work table `MIG_WORK.WF0006_SEG_02_OUT` (contract C3's name for this segment's primary stream) is rebuilt by every run and never appended to, so running the handler twice from the same input leaves the same rows. `scripts/validate_snowpark.py` checks exactly that, by running it twice in two fresh local-testing sessions and comparing the outputs as row multisets.
- The handler names two tables, both literals: its own input `MIG_WORK.WF0006_SEG_01_OUT` and its own output `MIG_WORK.WF0006_SEG_02_OUT`. It reads no mapped source and writes no mapped target, so `src_db`, `src_schema`, `tgt_db`, `tgt_schema` and `run_id` are all unused — contract C4 fixes the signature regardless.
- Needs verification on Snowflake: nothing in this segment has run anywhere but the Snowpark **Local Testing Framework**, which is an in-memory implementation, not an account. Whether the declared `RUNTIME_VERSION` and `PACKAGES` in `proc.sql` are ones a given account offers is unverified, and so is whether a real warehouse's pandas gives bit-identical floats for `min` and `round` on the same doubles.
