# wf_0003 / seg_02 — translation notes

One assumption per line. Nothing below has been checked against a real Alteryx engine or a real
Snowflake account; every claim is against `docs/reference/simulator-semantics.md` (the parity
oracle) and program spec §8.

- The segment holds tools 4–10 and reads `MIG_WORK.WF0003_SEG_01_OUT`, `seg_01`'s work table, written as a literal `MIG_WORK.…` name because contract C4 reserves `IDENTIFIER(…)` for mapped sources and targets.
- Output tool 10 becomes three statements in Alteryx's own order: the PreSQL, the write, the PostSQL. Contract C4 allows no variable beyond the `LET` that builds the target's name, so the whole tool chain lives inside the MERGE's `USING` subquery as one `WITH` list rather than being materialised into a scratch table.
- Tool 4's `ORDER BY` is `ACCT ASC NULLS FIRST, POSTED_DT ASC NULLS FIRST, ENTRY_ID DESC NULLS LAST` — the oracle's rule that NULL sorts first ascending and last descending, written out.
- The same three keys are repeated in every window's `ORDER BY` below instead of being taken from `t4_sort`: the row order of a CTE is not a promise in either dialect, and an order-dependent tool that relied on it would be correct only by accident.
- Tool 5 keeps the FIRST row of each `(ACCT, POSTED_DT)` in incoming order, and incoming order is tool 4's sort, so `QUALIFY ROW_NUMBER() OVER (PARTITION BY ACCT, POSTED_DT ORDER BY <the sort keys>) = 1` keeps the same row the Unique tool does — the one with the largest `ENTRY_ID` for that account and day.
- `PARTITION BY` treats NULLs as one group, which is the rule Unique uses: two rows of the same `ACCT` with a NULL `POSTED_DT` are the same key.
- Tool 5's Duplicates anchor is not wired, so no `D` branch is built; the rows it would carry simply leave the workflow.
- Tool 6's `[Row-1:RUN_BAL] + [AMOUNT]` with `OtherRows` = 0 is a running total of `AMOUNT` within `ACCT` in incoming order, so it is `SUM(AMOUNT) OVER (PARTITION BY ACCT ORDER BY <the sort keys> ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`.
- The running total is summed over the exact `NUMBER` amounts and cast to `FLOAT` once, because `RUN_BAL` is a `Double` field and the oracle converts an exact decimal to the nearest binary double at that field boundary. The oracle does that conversion on *every* row and then reads the previous row's double back through `Decimal(repr(x))`; one window sum cast once agrees with it for every amount in the four golden sets (each has at most two decimals and the totals stay small), but a running total long enough to lose a double's precision would not.
- Tool 7's Record ID becomes `ROW_NUMBER() OVER (ORDER BY <the sort keys>)` in first position, starting at 1. The column-name policy is `sanitize`, so Alteryx's `RecordID` is written `RECORD_ID`.
- `RECORD_ID` never reaches the target — tool 9 drops it — but it is what makes tool 9's `Last` expressible, so it is still a real column of the chain rather than an inlined expression.
- Tool 8's `IIF(DateTimeFormat([POSTED_DT], "%Y-%m-%d") = [User.PeriodEnd], "Y", "N")` becomes `IFF(TO_CHAR(POSTED_DT, 'YYYY-MM-DD') = '2026-08-31', 'Y', 'N')`: `[User.PeriodEnd]` is a workflow constant whose text value is resolved at translation time.
- A NULL `POSTED_DT` makes `TO_CHAR` NULL and the comparison NULL, and a NULL condition takes the else branch in both Alteryx's `IIF` and SQL's `IFF`, so such a row is flagged `'N'` and never NULL.
- Local-runtime fact, verified: `TO_CHAR(<timestamp>, 'YYYY-MM-DD')` keeps its format through sqlglot (it becomes `STRFTIME`), where a plain `CAST … AS TEXT` would print a full timestamp and never equal the date text.
- Tool 9's `Count` is `COUNT(*)`: Alteryx's `Count` counts rows, not values, so the `edge` set's NULL-`ENTRY_ID` row still counts as one entry. `CountNonNull` would have been `COUNT(ENTRY_ID)`.
- Tool 9's `Sum` of a `FixedDecimal` stays a `FixedDecimal`, so `TOTAL` is cast to `NUMBER(19,2)` — the Alteryx field's own width — rather than left at whatever width `SUM` widens to.
- Tool 9's `Last` takes the group's last row in incoming order, NULL included. Neither dialect has an ordered aggregate for that, so it is `MAX_BY(RUN_BAL, RECORD_ID)`: `RECORD_ID` is a row number, so it is unique, so its maximum inside a group is exactly that group's last row.
- Assumption, unproven by this sample's data: `MAX_BY` is only equal to Alteryx's `Last` while the last row's value is not NULL. `RUN_BAL` is a running total of a `NOT NULL` column, so it is never NULL here; a `Last` over a nullable column would need a different spelling.
- **Fixed gap in the golden data (fix round 1):** the `normal` set's `(4000, 2026-08)` group now carries a fifth row, `ENTRY_ID` 14, posted `01/09/2026` (so it sorts after entries 1–4 in `RUN_BAL` order) with `AMOUNT` `-400.00`, which pulls the group's running balance back down below the peak entry 3 set. Before this row, every `(ACCT, PERIOD)` group's running balance happened to reach its largest value on its own last row, so replacing `MAX_BY(RUN_BAL, RECORD_ID)` with `MAX(RUN_BAL)` still passed all four golden sets — a real translation mistake no set could catch. Now it does: the broken variant `04_last_translated_as_max.sql` demonstrates the mistake and FAILs on `normal` (see `samples/wf_0003/broken_sql/broken.json`).
- Tool 9's `Max` over a string ignores NULL in both the oracle and SQL, so `HAS_PERIOD_END` is a plain `MAX(PERIOD_END_FLAG)`; `'Y'` sorts above `'N'`, which is what makes it a flag.
- Tool 9 emits its groups ascending with NULL first. That order is not reproduced, and does not need to be: a MERGE's result does not depend on the order its source rows arrive in.
- Tool 10's `Update; Insert if new` on `ACCT, PERIOD` is a `MERGE` on exactly those keys. `T.ACCT = S.ACCT AND T.PERIOD = S.PERIOD` is NULL when a key is NULL, so a NULL key matches nothing and the row is inserted — which is what the oracle says Alteryx does, and why the `edge` set's NULL-`ACCT` group appears as a new row.
- The `USING` subquery's final `SELECT` is `t9_summarize`, grouped by exactly `ACCT, PERIOD` — the same pair the `MERGE`'s `ON` clause joins on — so it can produce at most one source row per distinct key, and this `MERGE` can never hit Snowflake's nondeterministic-merge error (multiple `USING` rows matching one target row). Needs verification on Snowflake.
- Alteryx maps incoming columns to the target BY NAME and writes only those, so the MERGE names the six the Summarize produced and never mentions `LOADED_FLAG`: it is left untouched on a matched row and arrives NULL on an inserted one.
- The `WHEN MATCHED THEN UPDATE SET` list is written unqualified (`TOTAL = S.TOTAL`), which is valid Snowflake; the local runtime rejects a qualified assignment target (`T.TOTAL = …`) outright, so the unqualified form is the only spelling that both accepts.
- The PreSQL `DELETE FROM dbo.GL_SUMMARY WHERE PERIOD < '2020-01'` keeps its predicate verbatim and is retargeted at the mapped table through `IDENTIFIER(:GL_SUMMARY_TGT)`, the name the body's `LET` builds; the source database's own table name never appears in the procedure.
- The PostSQL fills only NULLs, so a row the target already held with `LOADED_FLAG` `'N'` keeps its `'N'`; a translation that set the flag for every row would silently rewrite history, which is what the broken variant `02_postsql_not_translated.sql` exists to contrast with.
- The golden output is the target's state after all three statements, not this run's rows: a row the run does not touch (`9999`) is part of what is compared, and `PERIOD < '2020-01'` is gone before anything is written.
- `contract.outputs[0].columns` therefore lists all seven columns of the target, `LOADED_FLAG` included, and `keys` is `["ACCT", "PERIOD"]` — the Output tool's own update keys. No golden set holds two rows with the same key, so the comparison is a keyed diff and can name the column behind a difference.
- `ordering.order_dependent_columns` is `["CLOSING_BAL"]`: it is the one target column whose value depends on which row of a group came last. `TOTAL`, `ENTRIES` and `HAS_PERIOD_END` are order-free aggregates, and `RECORD_ID` — the textbook order-dependent column — does not reach the target.
- Needs verification on Snowflake: the local runtime types `NUMBER(19,2) + NUMBER(19,2)` (and a `SUM` over it) as scale 2, which is what Snowflake's addition rule gives too; the multiplication rule that makes scale `min(S1 + S2, max(S1, S2, 12))` is not reached by this segment, because nothing here multiplies.
- Needs verification on Snowflake: `MERGE`, `QUALIFY`, `MAX_BY` and `TO_CHAR(<timestamp>, fmt)` are all documented Snowflake SQL and all run on the local DuckDB double, but no statement in this file has been executed on an account.
- `RUN_ID` is unused: contract C4 fixes the parameter list, and neither the PreSQL nor the PostSQL this workflow carries has anywhere to record it.

## Nodes with no CTE

- tool 10 has no CTE: an Output Data tool is a write, not a computation — here it is the three statements (PreSQL `DELETE`, the `MERGE` whose `USING` subquery ends at `t9_summarize`, PostSQL `UPDATE`) that contract C4's flat statement list spells out in place of Alteryx's one tool.
